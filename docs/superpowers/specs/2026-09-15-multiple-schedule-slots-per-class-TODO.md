# Multiple Weekly Schedule Slots Per Class — TODO (not yet implemented)

> **Status: design only, deliberately not implemented.** Captured here so the decisions aren't lost. Do not start implementation without re-confirming this is still wanted — revisit the open question at the bottom first.

## Context

Today, a `Class` has exactly one weekly pattern: `dayOfWeek` + `startTime` + `durationMinutes`. The request is to let a class run multiple times per week — possibly more than once on the same day, possibly on different days — while forbidding two of that class's own slots from overlapping on the same day.

## Confirmed decisions

1. **Occurrence granularity**: each `(date, slot)` pair remains an independent occurrence — own materialized session, own attendance, independently reschedulable/cancellable. No change to the existing per-occurrence model, just more weekly patterns feeding into it.
2. **Overlap scope**: only checked within one class's own slots. Two different classes for the same operator may still overlap (matches today's behavior — nothing currently prevents two separate classes sharing a time).
3. **Update semantics**: `PUT /classes/{id}` accepts a `schedule` array and **replaces the whole slot list** at once (no separate add/remove-slot endpoints).
4. **Removed-slot sessions**: when a schedule update removes a slot, any future materialized session generated by that slot is **auto-cancelled** (soft-deleted) as part of the update. This is a deliberate, narrow exception to this feature's otherwise-consistent rule that class updates never touch existing sessions — it applies only to sessions tied to a slot that no longer exists, not to every session when any slot changes.
5. **Migration**: migrate existing classes' single pattern into the new shape rather than starting fresh (existing data must not be lost).
6. **Applies uniformly to both operator types** (`schedule` and `assigned`) — no special-casing. `assigned`-type's `maxSize: 1` constraint is about roster size, unrelated to schedule shape.

## Chosen schema approach

New table `class_schedule_slots`, plus a `slotId` FK on `sessions` (chosen over child-table-without-FK for precise, direct "cancel sessions from a removed slot" instead of inferring it from timestamps):

```sql
CREATE TABLE class_schedule_slots (
    id                BIGSERIAL PRIMARY KEY,
    class_id          BIGINT     NOT NULL REFERENCES classes (id) ON DELETE CASCADE,
    day_of_week       SMALLINT   NOT NULL,
    start_time        TIME       NOT NULL,
    duration_minutes  INTEGER    NOT NULL,
    created_at        TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    updated_at        TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT class_schedule_slots_day_of_week_check CHECK (day_of_week BETWEEN 0 AND 6),
    CONSTRAINT class_schedule_slots_duration_check CHECK (duration_minutes > 0)
);
```

No soft-delete on slots — hard-replaced (delete old rows, insert new ones, in one transaction) on every `PUT` that includes `schedule`.

`classes` drops `day_of_week`, `start_time`, `duration_minutes` (moved to the child table).

`sessions` gains `class_schedule_slot_id BIGINT NULL REFERENCES class_schedule_slots (id) ON DELETE SET NULL` — nullable because true one-off sessions and makeup sessions have no slot. `ON DELETE SET NULL` rather than `CASCADE`, so a slot's removal never silently destroys historical session/attendance rows outright; the update flow explicitly cancels (soft-deletes) affected sessions itself (decision 4), it doesn't rely on the FK's delete behavior to do that.

## Migration plan

1. For each existing `classes` row, insert one `class_schedule_slots` row copying its current `day_of_week`/`start_time`/`duration_minutes`.
2. Backfill `sessions.class_schedule_slot_id` for every session where `class_id` matches and `is_makeup_session = false`, pointing at that class's one migrated slot.
3. Drop `day_of_week`, `start_time`, `duration_minutes` from `classes`.
4. As with every prior schema change in this repo: hand-applied via a throwaway `pg` script (no migration tooling exists) + `docs/db/schema.sql` updated in the same change.

## Derivation changes

`computeOccurrenceDates` (in `class-occurrences.server.ts`) becomes: for each of the class's slots, run today's per-slot day-of-week walk independently, then merge all slots' dates and sort. Each virtual occurrence carries which slot produced it. Occurrence identity becomes `(classId, date, slotId)` instead of `(classId, date)`.

`materializeOccurrence(classId, date)` becomes `materializeOccurrence(classId, date, slotId)` — needs to know which slot's occurrence on that date, since a class can now have more than one occurrence on the same calendar day.

Nightly backfill job: tracked per `(classId, slotId)` pair instead of per class — same "day after the slot's latest materialized session through yesterday" logic, run once per slot.

## Overlap validation

On create/update, for the submitted slot list: group by `dayOfWeek`; within each day, reject if any two slots' `[startTime, startTime + durationMinutes)` windows intersect. Checked once against the whole list, in the same place `validate()` already checks `maxSize`/`minSize` bounds.

## API surface changes

- `POST /classes`: replace flat `dayOfWeek`/`startTime`/`durationMinutes` fields with `schedule: [{dayOfWeek, startTime, durationMinutes}, ...]` (min 1 entry required).
- `PUT /classes/{id}`: `schedule` becomes an optional replace-all field, same array shape. When present, triggers decision 4's auto-cancel of future sessions from removed slots.
- `GET /classes/{id}` and the list endpoint: `Class` response includes `schedule: [{id, dayOfWeek, startTime, durationMinutes}, ...]` instead of the flat fields.
- `GET /classes/{id}/occurrences/future|past`: each entry gains a `slotId` (and likely `dayOfWeek`/`startTime` for display convenience), since a date alone no longer identifies a single occurrence.
- **Open design question, not yet resolved**: the date-addressed action endpoints (`PATCH .../occurrences/{date}/reschedule`, `POST .../occurrences/{date}/cancel`, `PUT .../occurrences/{date}/attendance`) currently key on `{date}` alone. With multiple slots, one date can have multiple occurrences, so these need either `{date}/{slotId}` in the path or `slotId` as a required query/body param. **This was not resolved before work was paused — settle it before implementing.**

## Explicitly not addressed / deferred within this TODO

- Exact wire format for the overlap-validation error response (which slot(s) conflict, field naming).
- Whether swagger schema fidelity for the new `Occurrence`/`Class` shapes should get full named schemas or stay at this codebase's existing mixed inline-object fidelity level (see class-occurrences.controller.ts's existing precedent either way).
